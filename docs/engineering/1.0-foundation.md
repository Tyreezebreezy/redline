## Dictation 2.0 requirements

Dictation owns a session tied to one document and one mapped insertion anchor.
Recognition has two text states:

- Partial text is ephemeral UI state outside the ProseMirror document. It can
  churn, be cancelled, or disappear on failure.
- Committed text is inserted once through a normal ProseMirror transaction and
  immediately becomes user-owned document text.

The non-negotiable rule is **user edits win**. No later ASR result may target or
replace a committed segment. Further speech appends at the still-mapped session
anchor. A touched/deleted anchor, document switch, restore, close, or session
generation mismatch refuses further insertion and stops the session.

Start, stop, pause/resume, cancel-current-partial, microphone loss, engine
shutdown, and document close must all be explicit states. Pause stops chunk
delivery but may retain the visible partial; cancel clears only that partial.
Stop may finalize one pending segment. Failure clears partial audio/text and
closes the microphone. Audio remains bounded and process-memory-only.

Future cleanup is three separate stages: Verbatim, conservative Clean
Transcript, and optional/advisory Voice Polish. Neither cleanup nor the future
Humanizer may silently rewrite committed text.

## ASR probe and method

The development-only Rust harness in `probes/dictation-2/` uses REDLINE's
existing 26-fixture WAV corpus. It feeds sherpa in 100 ms chunks and re-decodes
Whisper over cumulative two-second prefixes. WER is case- and
punctuation-insensitive word edit distance. Report JSON stays in ignored
`src-tauri/target/redline-1.0-research/`.

Test host: Windows x64, Intel Core i9-11900K, 16 logical processors. Resource
sampling used one 12.325-second technical fixture. CPU percentages are average
share of total machine logical-CPU capacity, not instantaneous peaks.

The Whisper cumulative prototype preserves the current engine's accuracy but
repeats growing work. It cannot keep up with live speech on this host. Its
first partial includes the two-second capture prefix plus repeated inference,
and cost grows with utterance length.

Sherpa produces real incremental results and stays far below real time. Its
partials churn more often and this small English model is materially less
accurate. It emits uppercase text without punctuation, so a separate local
punctuation stage would be needed before production-quality commits.

The final-latency row is a conservative offline-replay proxy: source audio
duration plus total fixture processing time. It is comparable across these two
probes, but it is not an endpoint-to-committed-editor measurement. The hybrid
follow-up must measure that missing interval directly before production work.

Sherpa long-session results using repeated recorded speech:

| Audio | Processing | RTF | WER |
| ---: | ---: | ---: | ---: |
| 36.975 s | 1.410 s | 0.04 | 0.41 |
| 147.900 s | 4.970 s | 0.03 | 0.40 |
| 345.100 s | 11.777 s | 0.03 | 0.40 |

A 36.975-second Whisper cumulative-window run took 145.493 seconds (3.94 RTF),
produced 15 partial changes, and scored 0.095 WER on the repeated fixture. Its
accuracy improved with more context, but it fell further behind live audio.
Two- and five-minute runs are not practical because this method repeats
cumulative inference and is already almost four times slower than real time.

### Windows dependency finding

The default sherpa static Windows archive uses the static MSVC runtime
(`MT_StaticRelease`). Linking it into the same executable as REDLINE's
dynamic-runtime Whisper build failed with `LNK2038` and `LNK1169`. The
official sherpa shared feature built and ran with both wrappers in one process.
That mode copies `sherpa-onnx-c-api.dll`, `sherpa-onnx-cxx-api.dll`,
`onnxruntime.dll`, and `onnxruntime_providers_shared.dll` next to the
executable. A future product integration should package only runtime DLLs proven
necessary and verify their hashes.

The official model archive is 127,887,156 bytes. Its SHA-256 is
`9C559283E8498D3FE95913C79CA1CB454BB26281AC2B102B41306C7D752765D9`.
Only the four int8 recognition files total 45,202,074 bytes. The model README
declares Apache-2.0; sherpa-onnx and its Rust crates are Apache-2.0.

## Live editing prototype

`probes/dictation-live.mts` is a deterministic state prototype. It proves:

- partial text remains separate from committed segments;
- a commit happens once and duplicate finals are ignored;
- editing an earlier committed segment does not give ASR a replacement handle;
- later speech appends a new segment;
- pause/resume, partial cancel, microphone loss, document mismatch, and document
  close cannot mutate committed text.

It does not capture a microphone or modify Tiptap. Production integration still
needs mapped-anchor transactions, focus/selection QA, crash cleanup, and actual
WebView2 microphone sessions. This limitation is intentional while engine
quality remains unresolved.

## Dictation recommendation

Recommendation: **C. Continue with a bounded hybrid experiment, not production
replacement yet.**

Use sherpa only for fast local partials and endpoint detection, then evaluate
the existing Whisper model once per completed phrase for the final candidate.
Keep that candidate outside the document until finalization; after insertion,
never revisit it. This directly combines sherpa's measured latency/resource
advantage with Whisper's better measured accuracy.

The next experiment must measure endpoint-to-Whisper-final latency, combined
peak memory, punctuation quality, phrase duplication, real microphone behavior,
and user editing during a live session. If finalization remains too slow, do
not ship the hybrid; benchmark one better-accuracy streaming model within the
same sherpa runtime before revisiting architecture.

The approved hybrid experiment is documented in
`docs/engineering/dictation-2-hybrid.md`. Fixture accuracy, endpoint timing,
resources, long sessions, rapid-phrase backlog, and mapped-editor safety are
measured. Real laptop microphone evidence remains pending, so production
integration is not approved.

## Terminology Engine foundation and production follow-on

The prototype below established the boundary. On
`codex/redline-1.0-refactor-terminology`, it was productionized as a 377-record
generated snapshot with 203 high-confidence, 158 multiword-high-confidence,
and 16 context-required records. The offline source manifest, deterministic
generator, validation, ambiguity controls, update process, and current
performance evidence are documented in `terminology-engine.md`. There is still
no runtime network path or terminology-management UI.

### Original prototype evidence

The AXIOM hard-coded two-term array is replaced by a small generated-data seam:

- `terminology.v1.json`: 26 records, 26 aliases, 20 high-confidence and six
  context-required records.
- `terminology.ts`: dependency-free Unicode tokenization, case-insensitive
  exact aliases, longest multiword match, and adjacent-context checks.
- Existing `CanonicalTerm` issues remain editor-neutral projected-text issues.
  Existing protected-span filtering still runs after terminology matching.

High-confidence examples include YouTube, GitHub, LinkedIn, LinkedIn Learning,
Facebook Marketplace, PowerShell, ChatGPT, OpenAI, Microsoft 365, Visual Studio
Code, iPhone, and macOS.

Ambiguous Windows, Discord, Apple, Edge, Teams, and Android require an adjacent
product/service hint. Tests distinguish `windows 11` from `cleaned the
windows`, `discord server` from `discord among the teams`, and `edge
browser` from `edge of the table`. URLs, filenames, identifiers, and existing
protected spans remain excluded by AXIOM.

Future precedence is:

1. generated REDLINE built-in snapshot;
2. User Profile terminology overrides;
3. project/document Style Guide overrides.

Later layers override earlier ones and may suppress a built-in term. Personal
names such as ICARUS or The Forge are not added globally.

### Wikidata source and update path

Wikidata structured entity data is CC0. On 2026-09-15, the official dump index
reported `latest-all.json.bz2` dated 2026-09-09 at 103,048,420,178 bytes.
The application must never download or query it at runtime.

The recommended offline generation job is:

1. explicitly download and hash one dated JSON entity dump;
2. stream-decompress it line by line;
3. retain English labels and aliases only for a reviewed allowlist of software,
   service, company, product, operating-system, language, development-tool,
   cloud, education, and major-platform entity classes;
4. reject descriptions and prose;
5. retain QID, label, selected aliases, entity type, dump date, and confidence;
6. score common-word aliases as context-required and send them to paired-fixture
   review;
7. emit a versioned compact JSON snapshot and review its diff before release.

The source JSON format is a stable Wikidata interface and places each entity on
its own line. Full-dump ingestion was not performed because a 103 GB source is
unnecessary to validate the runtime architecture. The bounded seed uses
verified factual labels/QIDs and records retrieval/version metadata.

Update snapshots manually as part of a release-quality corpus pass. Do not add
a model/data downloader, runtime networking, or automatic terminology refresh.

the footprint.

## Future engine boundaries

- AXIOM: objective correctness, protected spans, and high-confidence
  terminology only.
- Clarity: advisory wordiness, repetition, passive voice, awkwardness, and
  flow; never styled as grammar errors.
- Word Tools: on-demand definitions, synonyms, antonyms, precision, simpler or
  stronger alternatives, usage, pronunciation, and personal vocabulary.
- User Profiles: own dictionaries, terminology overrides, dictation
  preferences, goals, voice traits, snippets, and Transform preferences.
- Voice/Humanizer: optional advisory preservation of personal cadence,
  contractions, directness, skepticism, emphasis, and ordinary vocabulary.
- Tone: reader-perception labels with confidence, never correctness errors.
- Writing Goals: a small audience/purpose/formality context passed explicitly
  to advisory engines.
- Transform Studio: preview-first practical and original creative style packs;
  Old English and Early Modern English stay distinct.
- Style Guides: scoped preferred/discouraged forms, explanations, matching
  semantics, and ownership separate from built-in terminology.
- Snippets: profile-scoped explicit expansions.
- Reader Impact and citation/research tools: later, separate, and local-first
  unless the owner approves a new trust boundary.

## Refactor findings

Production follow-on: the two high-priority seams were resolved without a shell
rewrite. `DocumentEditor.tsx` now owns editor construction and plugin
registration, `useTransformWorkflow.ts` owns existing Transform coordination,
and `src-tauri/src/app.rs` owns Tauri startup and bounded command registration.
Document, AXIOM, persistence, Dictation, and Transform behavior remains on the
existing boundaries. The CSS and grammar-corpus modules were not split because
this pass did not require those changes.

High:

- `src/App.tsx` is 1,268 lines and owns intertwined document, AXIOM,
  dictation, Transform, focus, and dialog coordination. Extract stateful feature
  controllers before production live dictation; do not rewrite the shell.
- `src-tauri/src/lib.rs` is 1,009 lines. Split bounded command registration
  from application lifecycle only when the next native feature touches it.

Medium:

- `src/styles.css` is 1,549 lines with layered responsive patches. Group rules
  by existing semantic region during a dedicated visual refactor, preserving
  the verified 720x480 floor.
- `scripts/grammar-corpus.mts` is 1,584 lines and mixes import adapters,
  evaluation, reporting, and CLI handling. Split only if the next corpus source
  changes it.
- Dictation state is divided between `src/dictation.ts`,
  `src-tauri/src/dictation.rs`, and App coordination. A production streaming
  session needs one explicit state contract, not duplicate flags.

Low:

- Terminology generation and snapshot validation are now build-time commands
  over a reviewed bounded source manifest; no full-dump or runtime ingestion was
  added.
- No generic engine framework, event bus, global state library, or data-access
  abstraction is justified.
