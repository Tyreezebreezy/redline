# REDLINE 0.0.8 local dictation

REDLINE captures the Windows system-default microphone through the packaged WebView2 `getUserMedia` path. A local AudioWorklet downmixes the stream into a fixed 90-second PCM16 mono buffer, all media tracks are stopped before transcription, and one raw binary IPC payload is sent to the existing CPU-only whisper.cpp provider through whisper-rs. Rust resamples the audio to 16 kHz with Rubato. Audio is never written to a temporary or application-storage file.

## Accepted WebView2 capture path

The isolated packaged Tauri probe under `probes/webview2-capture` used the same Tauri 2.11.5, Wry 0.55.1, and installed WebView2 runtime as REDLINE. It selected `Default - Mic/Inst (Samson G-Track Pro) (17a0:0241)` at 48,000 Hz, mono, 16-bit and passed two separate 20-cycle open/capture/stop runs. All 40 cycles produced bounded non-silent PCM, every track reached `ended`, every stream became inactive, and no external request was observed.

WebView2 showed its normal user-controlled microphone prompt. Allow persisted across a process restart without re-prompting. Block returned `NotAllowedError: Permission denied`; repeated requests remained denied without activating the microphone, including after restart. REDLINE does not install a permission handler and does not auto-grant or override a denial.

Production uses a single raw `Uint8Array` IPC payload. At the verified 48 kHz PCM16 mono format, the hard 90-second ceiling is 8,640,000 bytes. Rust validates the session, headers, sample rate, even-byte PCM shape, and size before conversion or Whisper inference. There is no streaming IPC or second production capture backend.

## Native build toolchain

- Rust/Cargo 1.97.1
- Visual Studio Build Tools 2022 17.14.37
- MSVC 14.44.35207
- Visual Studio bundled CMake
- LLVM/Clang and libclang 22.1.8

The existing MSVC and bundled CMake toolchain compiled whisper.cpp, but whisper-rs-sys 0.15.0 runs bindgen and failed without `libclang.dll`. Its bundled bindings were also tested and rejected because their Linux layout assertions do not compile for Windows MSVC. The Visual Studio LLVM component could not be added on this Windows build (`5007`), so the official standalone LLVM 22.1.8 package was the only additional machine-wide installation.

CPAL 0.18.1 allows Windows crates 0.61 through 0.62. Cargo initially selected `windows-core` 0.62 beside Tauri's 0.61 and CPAL's COM implementations did not compile. `Cargo.lock` therefore retains the compatible 0.61.2 version already used by Tauri.

Native microphone QA on the system-default Samson G-Track Pro exposed a WASAPI failure at `IAudioClient::Initialize` (`E_INVALIDARG`, `0x80070057`) after the device was detected. CPAL 0.18.1 reported six native configurations: two channels at 48,000 Hz with a fixed 480-frame buffer in `U8`, `I16`, `I24`, `I32`, `F32`, and `F64`; its selected default was `F32`. Default and fixed buffers, integer and float formats, and the enumerated-device path failed identically.

An isolated CPAL 0.17.3 experiment enumerated 147 advertised combinations: two channels; `U8`, `I16`, `I24`, `U24`, `I32`, `I64`, and `F32`; rates 5,512, 8,000, 11,025, 12,000, 16,000, 22,050, 24,000, 32,000, 44,100, 48,000, 64,000, 88,200, 96,000, 176,400, 192,000, 352,800, 384,000, 705,600, 768,000, 1,411,200, and 1,536,000 Hz; and buffer range 0 through `u32::MAX`. These are CPAL conversion probes, not trustworthy hardware-native claims: CPAL 0.17.3 treats shared-mode conversion as supported. Its actual `GetMixFormat` default was two-channel 48,000 Hz `F32`.

The first isolated 0.17.3 run anomalously completed five 350 ms cycles with 31,680 samples per cycle and no callback errors. It failed the required repeatability gate: both REDLINE's pinned path and a fresh standalone 0.17.3 process then consistently rejected that same reported default at stream creation with `0x80070057`. Invalid zero-channel input was rejected cleanly, and the successful anomalous cycles used counters only, proving bounded probe memory, but disconnect callback behavior could not be validated because no reliable stream could be reopened. CPAL 0.17.3 is therefore not accepted or pinned.

REDLINE's rejected native sample configuration was not invented: it was the exact two-channel 48,000 Hz `F32` mix format returned by WASAPI. The approved WebView2 boundary replaces that failed production capture implementation; the evidence remains here to explain why native CPAL/WASAPI and Media Foundation were rejected.

### Direct WASAPI compatibility probe

An isolated `wasapi` 0.23.0 probe under `probes/wasapi-capture` bypassed CPAL and resolved the Windows default capture endpoint as:

- Endpoint ID: `{0.0.1.00000000}.{5338cc09-ce2d-466b-967d-2b6e0b136290}`
- Friendly name: `Mic/Inst (Samson G-Track Pro)`
- Description: `Mic/Inst`
- Interface: `Samson G-Track Pro`
- Native shared mix format: 2 channels, 48,000 Hz, IEEE float, 32 container bits, 32 valid bits, 8-byte block alignment, 384,000 bytes/second, channel mask `0x00000003`
- Default period: 100,000 hns (10 ms)
- Minimum period: 30,000 hns (3 ms)

The probe passed that exact `GetMixFormat` result to shared, event-driven `IAudioClient::Initialize` with automatic conversion disabled, a 100,000 hns buffer duration, and the required zero shared-mode periodicity. The first initialization failed before stream creation with `E_INVALIDARG` (`HRESULT 0x80070057`): `The parameter is incorrect.`

No audio buffer was allocated, no stream was started, and no samples were captured. The audio client and COM apartment were released when the failed probe exited. Per the approved failure gate, alternate durations, polling mode, crate versions, capture APIs, Whisper integration, 20-cycle runs, process-restart runs, microphone reopen checks, and unplug/replug testing were not attempted. The full initialization tuple tested is rejected even without CPAL; this result does not establish that the device-reported channel/rate/sample representation itself is unsupported.

The failed wrapper probe's exact initialization tuple was:

- Share mode: `AUDCLNT_SHAREMODE_SHARED` (`0`)
- Stream flags: `AUDCLNT_STREAMFLAGS_EVENTCALLBACK` (`0x00040000`), with no conversion flags
- Buffer duration: 100,000 hns
- Periodicity: 0 hns
- Session GUID: null
- Format: 40-byte `WAVEFORMATEXTENSIBLE`; tag `0xFFFE`, `cbSize=22`, 2 channels, 48,000 Hz, 384,000 bytes/second, 8-byte block alignment, 32 container bits, 32 valid bits, channel mask `0x00000003`, IEEE-float subformat `{00000003-0000-0010-8000-00AA00389B71}`

`wasapi` 0.23.0 freed the original COM allocation and passed a by-value copy of the complete extensible structure. Because the device returned the expected extensible tag and size, the crate did not reconstruct it from stereo/48 kHz/float fields; the content was preserved, but the original allocation itself was not passed through. The nonzero event buffer duration was inconsistent with the documented shared event-mode zero/zero requirement.

### Final raw WASAPI matrix

The final isolated probe uses only the official Windows Rust bindings to retain the raw `GetMixFormat` allocation. It hashes all 40 bytes, calls shared `IsFormatSupported` with that same pointer, verifies that the fingerprint is unchanged, and passes the same pointer directly to `Initialize`. Each case activates a fresh `IAudioClient` and obtains a fresh mix-format allocation.

Both cases resolved endpoint `{0.0.1.00000000}.{5338cc09-ce2d-466b-967d-2b6e0b136290}` and returned the same complete format fingerprint, `0x8394D821B92B2590`.

| Case | Share mode | Flags | Duration / periodicity | `IsFormatSupported` | `Initialize` |
| --- | --- | --- | --- | --- | --- |
| A: timer-driven | Shared | `0x00000000` | `0 / 0` | `S_OK` (`0x00000000`), no closest match | `E_INVALIDARG` (`0x80070057`) |
| B: event-driven | Shared | `EVENTCALLBACK` (`0x00040000`) | `0 / 0` | `S_OK` (`0x00000000`), no closest match | `E_INVALIDARG` (`0x80070057`) |

In both cases the exact failing stage was `IAudioClient::Initialize`, with Windows message `The parameter is incorrect.` The failures occurred before `GetBufferSize`, capture-service acquisition, event-handle registration, `Start`, or audio-buffer allocation. Failed clients and format allocations were released before the next case used a fresh client. Because neither case initialized, the 3-second capture, 20-cycle repetition, speech validation, restart, and post-exit microphone checks could not run. Per the decision gate, no further CPAL version, audio framework, or production capture change was attempted.

### Media Foundation capture probe

After low-level WASAPI investigation was stopped, an isolated synchronous Media Foundation Source Reader probe under `probes/media-foundation-capture` used the Windows 0.62.2 Rust bindings without a general audio framework. `MFStartup` succeeded with version `0x00020070`, and `MFEnumDeviceSources` returned three audio capture devices:

1. `Mic/Inst (Samson G-Track Pro)` — `{0.0.1.00000000}.{5338cc09-ce2d-466b-967d-2b6e0b136290}`
2. `Headset Microphone (CORSAIR VIRTUOSO XT Wireless Gaming Headset)` — `{0.0.1.00000000}.{61ed5057-c52e-4626-aae9-505bf5e01fbc}`
3. `Microphone (Logitech StreamCam)` — `{0.0.1.00000000}.{9ae8f58f-558b-47cc-b939-8e75a02417fa}`

For the selected Samson activation, the following stages returned `S_OK`:

- `IMFActivate::ActivateObject<IMFMediaSource>`
- `MFCreateSourceReaderFromMediaSource`
- `IMFSourceReader::GetNativeMediaType`
- `IMFSourceReader::SetCurrentMediaType` with a partial audio/PCM type
- `IMFSourceReader::GetCurrentMediaType`

The source native media type was 2-channel, 48,000 Hz, 32-bit IEEE float with 8-byte block alignment and 384,000 bytes/second. The negotiated Source Reader output was 2-channel, 48,000 Hz, 16-bit PCM with 4-byte block alignment and 192,000 bytes/second. That output would remain compatible with REDLINE's existing Rust mono conversion and 16 kHz resampling path.

The first synchronous `IMFSourceReader::ReadSample` failed before returning any sample with `E_INVALIDARG` (`HRESULT 0x80070057`), Windows message `The parameter is incorrect.` No audio bytes were captured or persisted. Error unwinding invoked `IMFMediaSource::Shutdown`, released Source Reader/source/activation objects, called `MFShutdown`, and uninitialized COM.

Because the first capture attempt failed, the 3-second sample validation, bounded-memory exercise, 20-cycle run, second-process repeat, post-exit reopen, and disconnect/reconnect checks could not proceed. Per the approved failure gate, no alternate PCM request, Media Foundation mode, DirectShow path, or general Rust audio framework was attempted. The separately approved WebView2 fallback was evaluated afterward.

The native provider hashes the bundled model before its first initialization. The successfully verified model and Whisper context are reused for the process lifetime; subsequent dictation sessions do not re-hash the model.

The model-only `.gitattributes` rule uses the already-installed Git LFS filter so the checkpoint does not store a 141 MiB normal Git blob.

## Security boundary

Only `start_dictation`, `stop_dictation`, and `cancel_dictation` are exposed to the main window. Dictation adds no network, camera, arbitrary filesystem, shell, process, or global-shortcut authority and does not broaden either CSP. `Permissions-Policy: microphone=(self), camera=()` makes the intended media boundary explicit. The microphone stream exists only during a visible user-initiated session and is stopped on stop, cancel, timeout, capture failure, document transition, or application close.

If WebView2 permission is denied, REDLINE reports the denial and instructs the user to close REDLINE, rename `%LOCALAPPDATA%\com.tyree.redline\EBWebView`, then reopen the app to receive a fresh prompt. The SQLite document database is stored separately beside that folder. REDLINE also points to Windows **Settings > Privacy & security > Microphone > Let desktop apps access your microphone** for the machine-wide gate. A one-click origin-permission reset is deferred because Tauri/Wry does not expose a permission-only reset through the existing bounded application interface; its available clear-all operation would also erase unrelated WebView state, and bespoke COM plumbing solely for that button would be disproportionate for 0.0.8.

## Benchmark fixtures

`benchmarks/dictation-corpus.json` declares 26 purpose-created cases. `scripts/generate-dictation-fixtures.ps1` generates speech with installed Windows desktop voices and creates deterministic silence/noise controls. It stores no personal conversation. The release benchmark reports word edits, exact matches, cold model load, processing time, and real-time factor, and hard-fails on false speech from silence/noise controls.

The approved fixture generator produced all 26 local WAV files with installed Windows desktop voices. The final post-Ponytail release benchmark completed in 101.6 seconds:

- 15 exact transcripts
- normalized word error rate: `0.215`
- cold model load: `391 ms`
- first processing pass: `4,572 ms` for 3.33 seconds of speech (`1.373` real-time factor)
- warm processing range: approximately `4,094` to `4,526 ms`
- 4-second silence: no insertion and no inference
- 1-second silence: no insertion and no inference
- 4-second deterministic noise: empty transcript; no hallucination

Punctuation fixtures were exact. Most errors were concentrated in acronyms, networking terms, numbers, IP addresses, and proper names; this is the expected accuracy ceiling of the approved CPU-only `base.en` model and is recorded rather than hidden. A final cold packaged run through the actual Samson/WebView2/raw-IPC/Rust/Whisper path settled in `4,667 ms`; the measured packaged warm run settled in `4,245 ms`. The UI remained responsive while inference ran off the main thread.
